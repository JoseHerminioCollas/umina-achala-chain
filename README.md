# umina-achala-chain

Hedera scripts for Umiña Achala: create the HTS token, validate HIP-412 metadata, and mint NFTs (IPFS pin + HCS provenance message).

## Layout

`src/` has one folder per step, and code shared by every step sits directly in `src/`. In each folder, the files named after an action are scripts you run (from the repo root, e.g. `node src/token/createUminaToken.js`); `lib.js` holds that step's checks and transaction building, kept apart so they can be tested without a network.

| Folder | Scripts | Helpers |
|---|---|---|
| `src/token/` | `createUminaToken.js` | `lib.js` |
| `src/topic/` | `createUminaTopic.js` | `lib.js` |
| `src/mint/` | `mintUminaNFT.js`, `validateMetadata.js` | `lib.js`, `formPost.js`, `metadataValidator.js` |
| `src/consignment/` | `associateToken.js`, `consignToMerchant.js`, `sellConsigned.js`, `endConsignment.js` | `lib.js` |
| `src/sale/` | `sellOwnItem.js` | `lib.js` |
| `src/record/` | `recordEvent.js` | `lib.js` |
| `src/` | | `keys.js` (ECDSA key parsing and the `TREASURY_KEY` check used by every script), `mirror.js` (reads HCS topic events from the testnet mirror node), `hcs.js` (builds HCS events with the envelope from umina-achala-chain#10, signs them with the optional `HCS_SUBMIT_KEY`, and waits for the receipt) |

## Scripts

- `src/token/createUminaToken.js` creates the HTS token on testnet: `node src/token/createUminaToken.js [env-file] [--dry-run]`. The env file defaults to `.env.testnet`. `--dry-run` checks it and prints the token parameters (no keys, no network). The token gets a 5% royalty to the treasury with a fallback fee of `FALLBACK_FEE_HBAR` HBAR (about USD 3, converted on the day of creation), and no metadata key, so NFT metadata is immutable. It prints the new token ID; save it as `UMINA_TOKEN_ID`.
- `src/token/lib.js` holds its env checks and the token transaction.
- `src/topic/createUminaTopic.js` creates an HCS topic on testnet: `node src/topic/createUminaTopic.js <provenance|display> [env-file] [--force] [--dry-run]`. `provenance` holds the item's history (MINT, SALE, ...) and is saved as `HCS_TOPIC_ID`; `display` holds what the site shows and is saved as `HCS_DISPLAY_TOPIC_ID` (data model: umina-achala-chain#10). The topic gets the public half of `HCS_SUBMIT_KEY` as its submit key, so only messages signed with it are accepted, and `HCS_ADMIN_KEY` as its admin key; both are required, and on testnet can be the operator key. A real run first checks the mirror node and refuses when the env variable already names an existing topic (`--force` skips this; a placeholder ID that does not exist is fine). `--dry-run` prints the topic parameters without keys and without touching the network. It prints the new topic ID; save it under the variable it names.
- `src/topic/lib.js` holds its env checks, the topic transaction and the existing-topic check.
- `src/mint/validateMetadata.js` validates a metadata file: `npm run validate`.
- `src/mint/mintUminaNFT.js` validates the metadata, pins the item's images and then the metadata to IPFS through Pinata, mints, then submits the MINT message to HCS: `node src/mint/mintUminaNFT.js <metadata-file> [--dry-run]` or `--form <post-file>` (one of the two is required). The metadata file lists the item's pictures in an input-only `images` array (each with a `file` path relative to the metadata file, and a `description`); `image` and `files` are set from the pinned CIDs. Test images and documents go in `samples/` (git-ignored). To simulate the whole mint form flow, run `node src/mint/mintUminaNFT.js --form json/sample-form-post.json`: the post (text fields, `attributes`, `images`, `documents`) is turned into a metadata file in `generated/` (git-ignored, `--out` changes it) and minted. Optional `documents` (pdf, glb) are pinned after the images. The `properties.stone_id` must look like `UMINA-2026-CH-03`. It needs `PINATA_JWT` (allowed to pin both files and JSON), `UMINA_TOKEN_ID`, `HCS_TOPIC_ID` and `SUPPLY_KEY` in `.env.testnet`. Before pinning, it reads the HCS topic from the mirror node and refuses a `stone_id` that already has a MINT event (`--force` mints it again) or a topic that does not exist. If it fails after pinning, it prints the pinned CIDs so they can be unpinned.
- `src/mint/lib.js` holds its env checks and the Pinata pin; `src/mint/formPost.js` turns a form post into a metadata file, and `src/mint/metadataValidator.js` checks metadata against the schema.
- `src/consignment/consignToMerchant.js` consigns a minted serial (see `umina-achala-documents/consignment.md`): the merchant associates the token, the treasury transfers the serial to them, and they grant UA (the operator) an NFT allowance; then the transfer is recorded in HCS as `ISSUED_TO_OWNER` (with the transfer as `ref`), so it needs `HCS_TOPIC_ID`: `node src/consignment/consignToMerchant.js <serial> [--dry-run]`. If a step fails after the NFT has moved, it says so, with the transfer transaction ID.
- `src/consignment/endConsignment.js` ends a consignment: the merchant revokes UA's allowance on the serial and returns the NFT to the Treasury, recorded in HCS as `TRANSFER` with reason `consignment_ended`: `node src/consignment/endConsignment.js <serial> [--keep] [--dry-run]`. The merchant must still hold the serial. `--keep` only revokes the allowance; the merchant keeps the NFT and no event is recorded, since ownership does not change.
- `src/consignment/sellConsigned.js` sells a consigned serial in one atomic transfer: the buyer pays in HBAR, 70% goes to the merchant and 30% to UA, UA moves the NFT with the allowance, then the SALE message goes to HCS: `node src/consignment/sellConsigned.js <serial> <price-hbar> [--dry-run]`. The buyer must have associated the token first.
- `src/consignment/associateToken.js` associates the Umiña token with the merchant or buyer test account, which must happen before it can receive an NFT: `node src/consignment/associateToken.js <merchant|buyer> [--dry-run]`. The consignment scripts are testnet only and need `MERCHANT_ID`, `MERCHANT_KEY`, `BUYER_ID` and `BUYER_KEY` (test accounts standing in for a merchant and a buyer).
- `src/consignment/lib.js` holds the 70/30 split, the token association and their env checks.
- `src/sale/sellOwnItem.js` sells an NFT UA holds itself, straight from the Treasury, in one atomic transfer: the buyer pays the price in HBAR to UA and the Treasury sends the NFT, then the SALE message goes to HCS: `node src/sale/sellOwnItem.js <serial> <price-hbar> [--dry-run]`. It checks first that the Treasury still holds the serial. The buyer must have associated the token (`node src/consignment/associateToken.js buyer`). Testnet only; needs `BUYER_ID` and `BUYER_KEY`, and `TREASURY_KEY` when the Treasury is not the operator.
- `src/sale/lib.js` holds its argument and env checks.
- `src/record/recordEvent.js` records a SALE or DELIVERED event in the provenance topic for something that already happened, after checking it against the ledger on the mirror node (umina-achala-chain#8). It never moves an NFT or HBAR; `sellConsigned.js` and `sellOwnItem.js` record their own sales, so this covers sales made wallet to wallet, paid off-chain or on a marketplace, and deliveries.
  - `node src/record/recordEvent.js sale <serial> --seller <id> --buyer <id> --nft-tx <tx-id> --payment <on_chain|off_chain> [--payment-tx <tx-id>] [--sold-for <amount> [--currency <code>]] [--stone-id <id>] [--dry-run]`: `--nft-tx` must show the serial going from the seller to the buyer; for `on_chain`, the buyer's HBAR payment must be in it or in `--payment-tx`, and must equal `--sold-for` when given; `off_chain` prices are recorded as stated. A SALE for the same `--nft-tx` is refused.
  - `node src/record/recordEvent.js delivered <serial> --buyer <id> [--method in_person] [--delivered-at <date-time>] [--proof <file>] [--stone-id <id>] [--dry-run]`: the buyer must hold the NFT and have a SALE on the topic, which becomes the event's `ref`. `--proof` is optional: a JSON file `{ "message", "signature" }` where the message is the one `--dry-run` prints, signed by the buyer's account key; it is checked and its hash recorded (`proof: "signed"`). Without it the event says `proof: "none"`. A second DELIVERED for the same sale is refused.
  - Every run reads the topic and the ledger; `--dry-run` does all the checks, prints the event and sends nothing.
- `src/record/lib.js` holds the argument parsing, the ledger checks and the proof check.
- `schema/hip412-umina-schema.json` is the metadata schema, and this repo's copy is the source of truth (umina-achala-chain#14; umina-achala-web will use it instead of its own copy). It requires `stone_id` in the form `UMINA-YYYY-XX-NN`, `stone_type`, `specimen_form` (`natural`, `worked` or `crafted`), an 11-digit `vendor_ruc`, `mining_concession` as the 9-digit INGEMMET Código Único, and `reinfo_id` as the miner's RUC (REINFO is tracked by RUC), with both RUCs' check digits verified; `materials` lists the materials of a multi-material specimen (one `host`, any number of `inclusion`). Fields that can change after mint (`reinfo_status`, `last_regulatory_check`, `sinceramiento_status`, `export_status`) record the state at mint; later changes are HCS events. `export_status` no longer has `current_location`: custody is an HCS event.
- `schema/stone-types.json` is the controlled list of stone types: id, English and Spanish names, kind, IMA species and default HS code. `stone_type` and every `materials[].stone_type` must be an id from it; there is no "other", so a new type is added to the list first. Ids are permanent (deprecate, never rename or delete). Fossils are listed only to be refused (Ley 31204).
- `src/mint/metadataValidator.js` checks the schema, then what a schema cannot: stone types against the list (not deprecated, not a fossil, exactly one host in `materials`), and the check digits of `vendor_ruc` and `reinfo_id` (umina-achala-chain#5). `src/mint/stoneTypes.js` holds the list checks and writes the `Stone Type`, `Materials` and `Form` attributes from the list, replacing hand-written ones. Before pinning, the mint posts a `COMPLIANCE` event (stone type, RUC, concession, REINFO, HS code) and puts its transaction ID in `compliance_proof_hcs`.
- `json/template.json` is the empty metadata template: fixed fields keep their values and everything else is `null`. The form post is copied into it and unfilled fields are removed. `json/example.json` is one filled-in record, kept for reference (no `image` or `files`; they are set at mint time). `json/sample-form-post.json` is a simulated form post.

Copy `.env.example` to `.env.testnet` and fill it in. Never commit `.env*` files. See `umina-achala-documents` for the guides.

Tests: `npm install && npm test`.
