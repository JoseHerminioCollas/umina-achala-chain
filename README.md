# umina-achala-chain

Hedera scripts for Umiña Achala: create the HTS token classes (Umiña for stones, Achala for jewelry made of Umiña stones), validate HIP-412 metadata, and mint NFTs (IPFS pin + HCS provenance message).

## Layout

`src/` has one folder per step, and code shared by every step sits directly in `src/`. In each folder, the files named after an action are scripts you run (from the repo root, e.g. `NETWORK=testnet node src/token/createToken.js`); `lib.js` holds that step's checks and transaction building, kept apart so they can be tested without a network.

| Folder | Scripts | Helpers |
|---|---|---|
| `src/token/` | `createToken.js`, `adminToken.js` | `lib.js` |
| `src/topic/` | `createTopic.js` | `lib.js` |
| `src/mint/` | `mintNFT.js`, `validateMetadata.js`, `importIma.js` | `lib.js`, `prepare.js` (mint step 1: checks, no network), `publish.js` (pin and mint), `umina.js` and `achala.js` (what each class does at each mint step, `mintSteps`), `formPost.js`, `metadataValidator.js`, `stoneTypes.js`, `images.js` |
| `src/consignment/` | `associateToken.js`, `consignToMerchant.js`, `sellConsigned.js`, `endConsignment.js` | `lib.js` |
| `src/sale/` | `sellOwnItem.js` | `lib.js` |
| `src/record/` | `recordEvent.js` | `lib.js`, `proof.js` |
| `src/display/` | `displayEvent.js` | `lib.js` |
| `src/catalog/` | `buildCatalog.js` | `lib.js`, `media.js` (the copies of photos, models and documents) |
| `config/` | | UA's values, read by the scripts (umina-achala-chain#34): `umina-achala.js` (royalty, commission, topic memos, image settings, the project name in messages), `umina.js` and `achala.js` (each token class: name, symbol, memo, env variable, `stone_id` prefix, schema, template), `testnet.js` and `mainnet.js` (env file, mirror node, enabled). `umina-achala.js` also holds the IPFS gateway the catalog reads through (`IPFS_GATEWAY` overrides it) and the sizes of the catalog's photo copies (`catalogMedia`). Secrets and Hedera IDs stay in `.env.testnet` / `.env.mainnet`. |
| `src/` | | `nfts.js` (who holds the NFTs a script moves, read from the mirror node at once, #28), `keys.js` (ECDSA key parsing and the `TREASURY_KEY` check used by every script), `mirror.js` (reads HCS topic events, NFT holders, every NFT of a token, the NFTs an account holds and when an NFT last arrived in an account, from the mirror node of the network), `ipfs.js` (reads a file through the IPFS gateway, as JSON or as bytes, with retries, for the catalog), `hcs.js` (builds HCS events with the envelope from umina-achala-chain#10, signs them with the optional `HCS_SUBMIT_KEY`, and waits for the receipt) |

## Scripts

- `src/token/createToken.js` creates an HTS token class: `NETWORK=testnet node src/token/createToken.js [env-file] [--token umina|achala] [--dry-run]`. The default is the Umiña class (stones, `UMINA_TOKEN_ID`); `--token achala` creates the Achala class (jewelry made of Umiña stones, `ACHALA_TOKEN_ID`, umina-achala-chain#15). Both classes share every setting below except name, symbol and memo; `adminToken.js` takes the same `--token`. `--token=achala` works too; an unknown option or class is refused before the env file is read. The env file defaults to the network's own (`.env.testnet`), and a file given must name the network. `--dry-run` checks it and prints the token parameters (no keys, no network). The token gets a 5% royalty (`config/umina-achala.js`) to the treasury with a fallback fee of `FALLBACK_FEE_HBAR` HBAR (about USD 3, converted on the day of creation), and no metadata key, so NFT metadata is immutable. It prints the new token ID; save it under the variable it names (`UMINA_TOKEN_ID` or `ACHALA_TOKEN_ID`).
- `src/token/lib.js` holds its env checks and the token transaction, the royalty fee shared with the fee update, and the admin command checks.
- `src/token/adminToken.js` uses the token's admin keys on testnet (umina-achala-chain#21), each command signed by its own key: `fees --fallback-hbar <hbar> [--royalty <percent>]` (`FEE_SCHEDULE_KEY`) replaces the royalty and fallback fee, e.g. when the HBAR price has moved the fallback fee away from about USD 3; `pause` / `unpause` (`PAUSE_KEY`) stops or allows every transfer; `wipe <serial> --account <id> --reason <text>` (`WIPE_KEY`) removes a serial from the account that holds it; `burn <serial> --reason <text>` (`SUPPLY_KEY`) burns a serial still in the treasury. wipe and burn check the holder first and record a `BURN` event (reason, `method`, and for wipe `from_id`); the reason is public and permanent, so no personal data. fees and pause record no event. `--dry-run` sends nothing: `NETWORK=testnet node src/token/adminToken.js <command> [serial] [options] [--token umina|achala] [--dry-run]`. When a piece of jewelry is taken apart, its Achala NFT is burned with `burn <serial> --token achala`; its Umiña stones are kept and can be mounted in another Achala. wipe and burn of an Umiña refuse a stone mounted in an Achala that still exists, also on `--dry-run`: burn the Achala first (umina-achala-chain#24).
- `src/pinata/unpinBurned.js` unpins from Pinata the IPFS files of burned NFTs that no existing NFT uses (metadata file, photos, documents): `NETWORK=testnet node src/pinata/unpinBurned.js [--dry-run]`. It reads every NFT of both tokens from the mirror node, burned ones included (their metadata stays there), and each one's metadata through the gateway. A CID any existing NFT uses is kept, so a document pinned again for a new mint stays pinned; if an existing NFT's metadata cannot be read it unpins nothing. Metadata is read 4 at a time with a line per NFT. `--dry-run` lists the CIDs and does not call Pinata; a real run unpins each with one call (30 s timeout) and skips a CID the account does not pin, so `PINATA_JWT` needs only the `unpin` scope (no pin list is read). Needs `UMINA_TOKEN_ID`, `ACHALA_TOKEN_ID` and `PINATA_JWT`. Nothing is sent to Hedera. `src/pinata/lib.js` holds the CID set logic and the Pinata calls.
- `src/topic/createTopic.js` creates an HCS topic on testnet: `NETWORK=testnet node src/topic/createTopic.js <provenance|display> [env-file] [--force] [--dry-run]`. `provenance` holds the item's history (MINT, SALE, ...) and is saved as `HCS_TOPIC_ID`; `display` holds what the site shows and is saved as `HCS_DISPLAY_TOPIC_ID` (data model: umina-achala-chain#10). The topic gets the public half of `HCS_SUBMIT_KEY` as its submit key, so only messages signed with it are accepted, and `HCS_ADMIN_KEY` as its admin key; both are required, and on testnet can be the operator key. Every run, `--dry-run` included, first checks the mirror node and refuses when the env variable already names an existing topic (`--force` skips this; a placeholder ID that does not exist is fine). `--dry-run` then prints the topic parameters without keys and sends nothing. It prints the new topic ID; save it under the variable it names.
- `src/topic/lib.js` holds its env checks, the topic transaction and the existing-topic check.
- `src/mint/validateMetadata.js` validates a metadata file, Umiña or Achala by its `stone_id`: `npm run validate`, or `node src/mint/validateMetadata.js json/achala-example.json`.
- `src/mint/mintNFT.js` validates the metadata, makes one image file per photo, pins them and then the metadata to IPFS through Pinata, mints, then submits the MINT message to HCS: `NETWORK=testnet node src/mint/mintNFT.js <metadata-file> [--token umina|achala] [--dry-run]` or `--form <post-file>` (one of the two is required). It mints an Umiña by default and an Achala with `--token achala` (see below). The metadata file names the item's photos in input-only fields (each with a `file` path relative to the metadata file, and a `description`): `main_image` (required) and `images` (up to 20 more, #35). Photos are processed with sharp (umina-achala-chain#7): JPEG, PNG or WebP only, checked by their real type (GIF, HEIC and RAW are refused; export iPhone photos as JPEG), up to 25 MB and about 100 megapixels. Each is turned upright from its EXIF orientation and re-encoded **without any metadata**, so no EXIF or GPS location of a mine reaches IPFS, into `generated/<stone_id>/` (the `--out` folder), as **one file per photo** (umina-achala-chain#42), at most 1600 px on the long side and never enlarged: a photo with transparency becomes a reduced-palette PNG (so a wallet shows it on its own theme), one without becomes a JPEG (quality 82); the limits are in `config/umina-achala.js` (`images`). `image` is the main photo's file and appears only there: it gets no `files[]` entry and no `is_default_file`. `files[]` has one entry per other photo, each with its SHA-256 `checksum`. The web site and the mobile app resize the files as they need, so no thumbnails are made. `--dry-run` lists the files it would make without writing them; `--images-only` writes them and prints what it would pin (including the metadata) and mint, without pinning, minting or needing any credentials. Testnet posts, images and documents live in the `umina-achala-testnet` repo, linked here as `testnet/` (git-ignored: `ln -s ../umina-achala-testnet testnet`). To simulate the whole mint form flow, run `NETWORK=testnet node src/mint/mintNFT.js --form testnet/chrysocolla_a.json`: the post (text fields, `attributes`, `main_image`, `images`, `documents`) is turned into a metadata file in `generated/` (git-ignored, `--out` changes it) and minted. Optional `documents` (pdf, glb) are pinned after the images. The `properties.stone_id` must look like `UMINA-2026-CH-03` (an Achala: `ACHALA-2026-RI-01`); metadata of the other class is refused with a hint to give `--token`. It needs `PINATA_JWT` (allowed to pin both files and JSON), `UMINA_TOKEN_ID`, `HCS_TOPIC_ID` and `SUPPLY_KEY` in `.env.testnet`. Before pinning, it reads the HCS topic from the mirror node and refuses a `stone_id` that already has a MINT event (`--force` mints it again) or a topic that does not exist. If it fails after pinning, it prints the pinned CIDs so they can be unpinned.
- **Minting an Achala** (umina-achala-chain#16): `NETWORK=testnet node src/mint/mintNFT.js --form testnet/achala_a.json --token achala`. An Achala is a piece of jewelry made of one or more Umiña NFTs, listed in `properties.stones` (`stone_id` and `serial`), all in the Umiña token named once in `properties.umina_token_id`: the mint fills it from `UMINA_TOKEN_ID`, also in the file generated from a form post, and refuses any other value. The buyer of an Achala gets it and each Umiña in it. A gold nugget is a stone, so it can be an Umiña, and a gold piece is an Umiña itself or an Achala made of a gold Umiña; `properties.metals` says where the gold or silver comes from (`source: "umina"` with the stone's `stone_id`, or `"invoice"` with the invoice in `documents`). It also needs `ACHALA_TOKEN_ID` and `TREASURY_ID`. Before posting anything, a real run checks every stone on the mirror node and the topic: in the Umiña token, matching its MINT event, not burned, held by the treasury, and not mounted in another Achala that still exists (`--force` does not skip this). COMPLIANCE carries the piece type, artisan, RUC, HS code and stone IDs; MINT adds `from_stone_ids`, which records the stones as mounted; the stones get no events of their own. The `Piece Type`, `Metal`, `Stones` (names from each stone's COMPLIANCE event) and `Artisan` attributes are written from the data. When a piece is taken apart, its Achala is burned (`adminToken.js burn` or `wipe`, `--token achala`); its `BURN` event unmounts the stones, whose Umiña NFTs are kept and can be mounted again.
- `src/mint/achala.js` holds the Achala checks (`achalaProblems`, `stoneLedgerProblems`, `mountedStones`), and its attributes.
- `src/mint/images.js` checks the photos and makes their versions with sharp (`inspectImage`, `planVersions`, `writeVersions`).
- `src/mint/lib.js` holds its command line (`parseMintArgs`), env checks per class and the Pinata pin; `src/mint/formPost.js` turns a form post into a metadata file, and `src/mint/metadataValidator.js` checks metadata against the schema.
- `src/consignment/consignToMerchant.js` consigns a minted serial (see `umina-achala-documents/consignment.md`): the merchant associates the token, the treasury transfers the serial to them, and they grant UA (the operator) an NFT allowance; then the transfer is recorded in HCS as `ISSUED_TO_OWNER` (with the transfer as `ref`), so it needs `HCS_TOPIC_ID`: `NETWORK=testnet node src/consignment/consignToMerchant.js <serial> [--token umina|achala] [--dry-run]`. If a step fails after the NFT has moved, it says so, with the transfer transaction ID. A stone mounted in an Achala is refused (umina-achala-chain#24). With `--token achala` the Achala moves with every stone in it, in one transfer, with one allowance approval and one event (#28); `sellConsigned.js` and `endConsignment.js` take the same option, and all three refuse a stone of an Achala on its own and check the holders on the mirror node first (`src/nfts.js`).
- `src/consignment/endConsignment.js` ends a consignment: the merchant revokes UA's allowance on the serial and returns the NFT to the Treasury, recorded in HCS as `TRANSFER` with reason `consignment_ended`: `NETWORK=testnet node src/consignment/endConsignment.js <serial> [--token umina|achala] [--keep] [--dry-run]`. The merchant must still hold the serial. `--keep` only revokes the allowance; the merchant keeps the NFT and no event is recorded, since ownership does not change.
- `src/consignment/sellConsigned.js` sells a consigned serial in one atomic transfer: the buyer pays in HBAR, and the merchant ends with 70% and UA with 30%, the 5% royalty included (#30); UA moves the NFT with the allowance, then the SALE message goes to HCS: `NETWORK=testnet node src/consignment/sellConsigned.js <serial> <price-hbar> [--token umina|achala] [--dry-run]`. The buyer must have associated the token first.
- `src/consignment/associateToken.js` associates a token with the merchant or buyer test account, which must happen before it can receive an NFT: `NETWORK=testnet node src/consignment/associateToken.js <merchant|buyer> [--token umina|achala] [--dry-run]`. With `--token achala` it associates both the Achala and the Umiña tokens, since an Achala moves with its stones (#28); a token already associated is skipped. The consignment scripts are testnet only and need `MERCHANT_ID`, `MERCHANT_KEY`, `BUYER_ID` and `BUYER_KEY` (test accounts standing in for a merchant and a buyer).
- `src/consignment/lib.js` holds the 70/30 split, the token association and their env checks.
- `src/sale/sellOwnItem.js` sells an NFT UA holds itself, straight from the Treasury, in one atomic transfer: the buyer pays the price in HBAR to UA and the Treasury sends the NFT, then the SALE message goes to HCS: `NETWORK=testnet node src/sale/sellOwnItem.js <serial> <price-hbar> [--token umina|achala] [--dry-run]`. It reads the provenance topic first (also on `--dry-run`) and refuses an Umiña mounted in an Achala that still exists (umina-achala-chain#24), then checks on the mirror node that the Treasury still holds every NFT that moves (also on `--dry-run`). With `--token achala` it sells an Achala with every Umiña in it, in the same transfer (N+1 NFTs, at most 10: the Achala and 9 stones, umina-achala-chain#26): the stones come from the Achala's MINT event and each stone's serial from its own MINT (a reminted stone: its serial that is not burned); the SALE names the Achala and adds `from_stone_ids`, `umina_token_id` and `umina_serials`. The buyer must have associated the token (`NETWORK=testnet node src/consignment/associateToken.js buyer`, with `--token achala` for an Achala: both tokens). Testnet only; needs `BUYER_ID` and `BUYER_KEY`, and `TREASURY_KEY` when the Treasury is not the operator.
- `src/sale/lib.js` holds its argument and env checks.
- `src/display/displayEvent.js` records what UA has for sale on its site, and at what price, on the display topic (`HCS_DISPLAY_TOPIC_ID`, umina-achala-chain#43): `LISTED` with a price in HBAR, and `UNLISTED` with an optional public `--reason`. The site's catalog (#44) lists an item only while its latest display event is a `LISTED`. Only items the Treasury holds are listed (Phase 2B: no consignment). Every run checks on the mirror node that the NFT exists, is not burned and is held by the Treasury, takes the `stone_id` from its `MINT`, and refuses to list an Umiña mounted in an Achala that still exists (the Achala is listed as one item at one price). A listing counts only if it was made after the NFT last arrived in the Treasury, so an item sold and returned is listed again by hand. Listing again at the same price is refused; a new price is a new `LISTED`. Only a listed item can be unlisted. `status` sends nothing: it shows every item the Treasury holds, whether it is listed and at what price. It never moves an NFT or HBAR.
  - `NETWORK=testnet node src/display/displayEvent.js listed <serial> --price <hbar> [--token umina|achala] [--dry-run]`
  - `NETWORK=testnet node src/display/displayEvent.js unlisted <serial> [--reason <text>] [--token umina|achala] [--dry-run]`
  - `NETWORK=testnet node src/display/displayEvent.js status [--token umina|achala]`
- `src/catalog/buildCatalog.js` builds the site's catalog, `catalog.json`, from the chain and IPFS (umina-achala-chain#44): only what UA has for sale, each item with its HIP-412 metadata, its price from `LISTED` and its provenance events, and an Achala with its mounted stones. An NFT is in it when it is not burned, the Treasury holds it, it has a `MINT`, it is not an Umiña mounted in an Achala that still exists, and its latest display event since it last arrived in the Treasury is `LISTED`; an Achala also needs the Treasury to hold each of its stones. Metadata is read through the IPFS gateway, except a CID already in the previous catalog, and checked against its schema; an item whose metadata is not valid is left out with a warning. If the mirror node or the gateway fails, the build stops and the old catalog stays. Each photo (an NFT's image and its image files, not documents or models) gets two WebP copies under `<out-dir>/media/<cid>/` (umina-achala-chain#45): `thumb.webp` (fitted inside 400 px) for the cards and `display.webp` (1080 px) for the detail view, transparency kept; `catalog.json` maps each photo's `ipfs://` URI to them in `media`. A copy already on disk is not read again (an IPFS file never changes), so only new photos are downloaded; a photo that cannot be read gets no copy, with a warning, and the site loads it through the gateway. Each 3D model (`model/gltf-binary`) and PDF document (`application/pdf`) in an NFT's `files` is copied unchanged, once, to `<out-dir>/media/<cid>/model.glb` or `document.pdf` (umina-achala-chain#46), mapped in `media` as `{ file }`, so the site never loads a file from the gateway on a visit; one that cannot be read gets no copy, with a warning. The build ends with the total size of `media/`. The first build of a full catalog reads every photo once and can take minutes on the public gateway. The file is written to a temp file and renamed. It only reads: nothing is sent to Hedera and no key is needed. Run by hand after a mint, a listing change or a sale, then publish it (umina-achala-web#89).
  - `NETWORK=testnet node src/catalog/buildCatalog.js <out-dir> [--dry-run]`
- `schema/catalog-schema.json` is the format of `catalog.json`, the contract with the site (umina-achala-web#124). The builder checks its output against it before writing. **Copy it to umina-achala-web when it changes.**
- `src/record/recordEvent.js` records a SALE or DELIVERED event in the provenance topic for something that already happened, after checking it against the ledger on the mirror node (umina-achala-chain#8). It never moves an NFT or HBAR; `sellConsigned.js` and `sellOwnItem.js` record their own sales, so this covers sales made wallet to wallet, paid off-chain or on a marketplace, and deliveries. `--token achala` records them for an Achala (umina-achala-chain#26): a SALE must show `--nft-tx` moving the Achala and every stone in its MINT from the seller to the buyer, and adds `from_stone_ids`, `umina_token_id` and `umina_serials`; a DELIVERED is one event on the Achala. Its `stone_id` comes from the Achala's MINT unless `--stone-id` is given.
  - `NETWORK=testnet node src/record/recordEvent.js sale <serial> --seller <id> --buyer <id> --nft-tx <tx-id> --payment <on_chain|off_chain> [--payment-tx <tx-id>] [--sold-for <amount> [--currency <code>]] [--stone-id <id>] [--token umina|achala] [--dry-run]`: `--nft-tx` must show the serial going from the seller to the buyer; for `on_chain`, the buyer's HBAR payment must be in it or in `--payment-tx`, and must equal `--sold-for` when given; `off_chain` prices are recorded as stated. A SALE for the same `--nft-tx` is refused.
  - `NETWORK=testnet node src/record/recordEvent.js delivered <serial> --buyer <id> [--method in_person] [--delivered-at <date-time>] [--proof <file>] [--stone-id <id>] [--token umina|achala] [--dry-run]`: the buyer must hold the NFT and have a SALE on the topic, which becomes the event's `ref`. `--proof` is optional: a JSON file `{ "message", "signature" }` where the message is the one `--dry-run` prints, signed by the buyer's account key; it is checked and its hash recorded (`proof: "signed"`). Without it the event says `proof: "none"`. A second DELIVERED for the same sale is refused.
  - Every run reads the topic and the ledger; `--dry-run` does all the checks, prints the event and sends nothing.
- `src/testnet/transferBetweenWallets.js` (testnet only) moves an NFT between the test merchant and the test buyer, signed by both: a sale made elsewhere, with or without HBAR (`--hbar`), to test the royalty and the fallback fee (umina-achala-chain#40). It refuses any other `NETWORK` before reading the env file. `NETWORK=testnet node src/testnet/transferBetweenWallets.js <serial>[,<serial>...] --from merchant|buyer [--to merchant|buyer] [--token umina|achala] [--hbar <amount>] [--dry-run]`.
- `src/record/lib.js` holds the argument parsing and the ledger checks; `src/record/proof.js` the delivery proof (the message the buyer signs and the signature check).
- `schema/hip412-achala-schema.json` is the Achala metadata schema: `stone_id` `ACHALA-YYYY-XX-NN`, `piece_type`, `stones` (1 to 9 Umiña NFTs, so an Achala and its stones fit in one transfer), optional `metals`, `technique`, `artisan_rna`, `hs_code`, `vendor_ruc` (check digit verified). Copy it to umina-achala-web too when it changes.
- `schema/hip412-umina-schema.json` is the Umiña metadata schema, and this repo's copy is the source of truth (umina-achala-chain#14). umina-achala-web keeps a copy of it and of `schema/stone-types.json` in its own `schema/` folder: **when either file changes here, copy it to umina-achala-web too.** It requires `stone_id` in the form `UMINA-YYYY-XX-NN`, `stone_type`, `specimen_form` (`natural`, `worked` or `crafted`), an 11-digit `vendor_ruc`, `mining_concession` as the 9-digit INGEMMET Código Único, and `reinfo_id` as the miner's RUC (REINFO is tracked by RUC), with both RUCs' check digits verified; `materials` lists the materials of a multi-material specimen (one `host`, any number of `inclusion`). Fields that can change after mint (`reinfo_status`, `last_regulatory_check`, `sinceramiento_status`, `export_status`) record the state at mint; later changes are HCS events. `export_status` no longer has `current_location`: custody is an HCS event.
- `schema/stone-types.json` is the controlled list of stone types: id, English and Spanish names, kind, IMA species and default HS code. `stone_type` and every `materials[].stone_type` must be an id from it; there is no "other", so a new type is added to the list first. Ids are permanent (deprecate, never rename or delete). Fossils are listed only to be refused (Ley 31204). Besides the curated entries, it holds the 6,239 IMA-approved mineral species (`source: "ima"`), imported with `node src/mint/importIma.js schema/sources/<export>.csv [--dry-run]` from an RRUFF IMA Mineral List export (https://rruff.net/ima-mineral-list/, "IMA Approved Minerals Only", CSV) kept in `schema/sources/`. Imported species have an English name only and no default HS code; curated entries always win. Re-running with a newer export adds new species and marks any that disappeared as deprecated, never deleting an id. After an import, copy the list to umina-achala-web.
- `src/mint/metadataValidator.js` checks the schema, then what a schema cannot: stone types against the list (not deprecated, not a fossil, exactly one host in `materials`), and the check digits of `vendor_ruc` and `reinfo_id` (umina-achala-chain#5). `src/mint/stoneTypes.js` holds the list checks and writes the `Stone Type`, `Materials` and `Form` attributes from the list, replacing hand-written ones. Before pinning, the mint posts a `COMPLIANCE` event (stone type, RUC, concession, REINFO, HS code) and puts its transaction ID in `compliance_proof_hcs`.
- `json/umina-template.json` is the empty metadata template: fixed fields keep their values and everything else is `null`. The form post is copied into it and unfilled fields are removed. `json/umina-example.json` is one filled-in record, kept for reference: it names its photos in `main_image` and `images` (the files in `testnet/`), and has no `image` or `files`, which are set at mint time; `NETWORK=testnet node src/mint/mintNFT.js json/umina-example.json --dry-run` shows what it would make. `testnet/chrysocolla_a.json` is a simulated form post. The Achala ones are `json/achala-template.json`, `json/achala-example.json` and `testnet/achala_a.json`.

Copy `.env.example` to `.env.testnet` and fill it in. Never commit `.env*` files.

Network: every script runs on the network named by `NETWORK`, set in the shell, and reads that network's env file (`.env.testnet`) and mirror node (`config/testnet.js`, `src/network.js`). **`NETWORK` has no default** (#34): a script refuses to run without `NETWORK=testnet` or `NETWORK=mainnet` in front of the command, so a forgotten variable never reaches either network. `validateMetadata.js` and `importIma.js` touch no network and need none. Mainnet is listed but not enabled until its keys and accounts are decided (#32). The shared startup (env file, problem output, operator client, closing it) is in `src/script.js`, and the shared environment checks in `src/env.js` (#29). Every script takes `--help` (or `-h`), and refuses an option or argument it does not take, so a mistyped `--dry-run` never sends a real transaction. The provenance topic is read through `src/provenance.js`. See `umina-achala-documents` for the guides.

Tests: `npm install && npm test`.
